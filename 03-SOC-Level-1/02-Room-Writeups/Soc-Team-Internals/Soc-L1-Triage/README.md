## 2. Introduction

Alert triage is one of the most important responsibilities of a Level 1 SOC Analyst.

Security systems continuously generate alerts based on suspicious activities detected across endpoints, networks, servers, and applications.

However, not every alert represents a real cyberattack. Some alerts are generated by legitimate activities, while others may indicate malicious behaviour.

A SOC L1 analyst must review these alerts, investigate the available evidence, determine whether the activity is suspicious, and decide the appropriate next action.

### Learning Objectives

- Understand how security events become alerts.
- Learn the difference between events and alerts.
- Understand important alert properties.
- Learn how to prioritize security alerts.
- Perform alert triage using a simulated SOC dashboard.
- Classify alerts as True Positive or False Positive.
- Understand the alert investigation and closure process.

## 3. Events and Alerts

### 3.1 What is a Security Event?

A security event is an observable activity recorded by a system, application, or network device.

Examples:

- A user logs into a computer.
- A process is executed.
- A file is downloaded.
- A user accesses a website.
- A firewall blocks a connection.
- A user attempts to access a restricted resource.

Events are recorded in logs and provide information about system activities.

### 3.2 What is a Security Alert?

A security alert is a notification generated by a security solution when an event or combination of events matches a detection rule or suspicious activity pattern.

Examples:

- Unusual Login Location.
- Email Marked as Phishing.
- Windows RDP Brute Force.
- Potential Data Exfiltration.
- Unapproved Mimikatz Usage.

### 3.3 From Events to Alerts

The general process:

1. An activity occurs on a system.
2. The system generates an event.
3. The event is recorded in logs.
4. Logs are forwarded to a security monitoring solution.
5. SIEM or EDR detection rules analyse the activity.
6. A suspicious event or pattern triggers an alert.
7. The SOC analyst investigates the alert.

### Events vs Alerts

| Events | Alerts |
|---|---|
| Record activities occurring in a system. | Highlight activities that require security attention. |
| Can be generated continuously. | Generated when detection conditions are met. |
| Most events may be normal. | May indicate suspicious or malicious activity. |
| Example: Successful user login. | Example: Login from an unusual location. |

### 3.4 Security Solutions Used for Alert Management

| Solution | Examples | Purpose |
|---|---|---|
| SIEM | Splunk ES, Elastic Security | Collects and analyses logs and manages security alerts. |
| EDR | Microsoft Defender, CrowdStrike | Monitors endpoints and detects suspicious activities. |
| NDR | Network Detection and Response solutions | Detects suspicious network activity. |
| SOAR | Splunk SOAR, Cortex XSOAR | Automates and coordinates security response workflows. |
| ITSM | Jira, ServiceNow | Supports incident and ticket management. |

### Role of SOC Teams in Alert Triage

**SOC L1 Analyst**
- Reviews incoming alerts.
- Performs initial investigations.
- Separates legitimate activity from potential threats.
- Escalates confirmed or complex threats.

**SOC L2 Analyst**
- Performs deeper investigations.
- Handles escalated incidents.
- Supports containment and remediation.

**SOC Engineer**
- Maintains security monitoring systems.
- Improves detection rules and alert quality.
- Ensures analysts receive useful alert information.

**SOC Manager**
- Oversees SOC operations.
- Monitors analyst performance.
- Ensures effective security monitoring and response.

## 4. Alert Properties

Before investigating an alert, an analyst must understand its important properties.

### Important Alert Fields

| Property | Description |
|---|---|
| Alert Time | Time when the security alert was generated. |
| Event Time | Time when the original activity occurred. |
| Alert Name | Short description of the detected activity. |
| Alert Severity | Indicates the potential urgency and impact. |
| Alert Status | Shows the current investigation state. |
| Alert Verdict | Indicates whether the alert is classified as a real threat or non-threat. |
| Alert Assignee | Analyst responsible for investigating the alert. |
| Alert Description | Explains the detection rule and why the alert was generated. |
| Alert Fields | Additional information such as hostname, username, IP address, and command line. |

### 4.1 Alert Severity

Severity helps analysts understand how urgently an alert should be investigated.

| Severity | Meaning |
|---|---|
| Critical | Potentially severe security threat requiring immediate attention. |
| High | Significant potential security risk. |
| Medium | Suspicious activity requiring investigation. |
| Low | Lower-risk activity or limited security impact. |
| Informational | Activity recorded for awareness or monitoring. |

**Important:** Severity is not the same as priority. Priority can also depend on business impact, asset importance, exposure, and other contextual information.

### 4.2 Alert Status

Alert status indicates the current state of an investigation.

| Status | Meaning |
|---|---|
| New | Alert has not yet been investigated. |
| In Progress | An analyst is currently investigating it. |
| Closed | Investigation has been completed and the alert has been resolved or classified. |

Different organizations may use additional statuses.

### 4.3 Alert Verdict

An alert verdict describes the analyst's conclusion.

**True Positive (TP)**

The alert correctly identifies actual malicious or unauthorized activity.

Example:
A detection identifies malicious credential-dumping activity that is confirmed during investigation.

**False Positive (FP)**

The alert is triggered, but investigation determines that the activity is not malicious.

Example:
A security rule identifies a legitimate administrative action as suspicious.

**Important:** A False Positive does not mean the detection system malfunctioned. It means the activity did not represent the threat indicated by the alert.

## 5. Alert Prioritisation

SOC teams can receive many alerts, so analysts must decide which alerts should be investigated first.

This process is called Alert Prioritisation.

### Recommended Prioritisation Workflow

**Step 1 – Filter Alerts**

- Identify new and unassigned alerts.
- Avoid investigating alerts already assigned to another analyst.
- Focus on unresolved alerts.

**Step 2 – Sort by Severity**

Generally, investigate in the following order:

1. Critical
2. High
3. Medium
4. Low
5. Informational

**Step 3 – Sort by Time**

When alerts have the same severity, prioritize older unresolved alerts before newer ones, unless other risk factors or organizational procedures require a different order.

### Why Is Prioritisation Important?

- Helps identify serious threats quickly.
- Reduces the risk of missing active attacks.
- Improves SOC efficiency.
- Helps analysts manage large alert volumes.
- Supports timely incident response.

### Alert Fatigue

Alert fatigue occurs when analysts receive too many alerts, especially repetitive or low-value alerts.

This can cause analysts to overlook genuine security threats.

Reducing false positives and improving detection rules can help reduce alert fatigue.

## 6. Alert Triage Process

Alert triage is the process of reviewing, investigating, classifying, and resolving a security alert.

### Step 1 – Initial Actions

Before beginning the investigation:

1. Select an appropriate unassigned alert.
2. Assign the alert to yourself.
3. Change its status to In Progress.
4. Review the alert name and description.
5. Identify the key information and indicators.

This ensures ownership and prevents multiple analysts from unnecessarily investigating the same alert.

### Step 2 – Investigation

This is the most important stage of alert triage.

The analyst must determine whether the detected activity is legitimate or malicious.

#### Understand Who Is Under Threat

Identify:

- Affected username.
- Hostname or endpoint.
- IP address.
- Network or cloud environment.
- Application or website.

#### Understand What Happened

Review the alert details to understand:

- What activity triggered the alert?
- Which detection rule generated it?
- When did the activity occur?
- Which user or system was involved?
- What security risk could the activity represent?

#### Review Surrounding Events

Investigate related events before and after the alert.

For example:

- Previous login attempts.
- Failed authentication attempts.
- Suspicious process executions.
- Unexpected file downloads.
- Unusual network connections.
- Changes in account activity.

#### Use Threat Intelligence

When appropriate, verify suspicious indicators using available threat intelligence sources.

Examples:

- IP addresses.
- Domains.
- URLs.
- File hashes.
- Known malicious indicators.

### Step 3 – Final Actions

After investigation:

1. Decide whether the alert is a True Positive or False Positive.
2. Write a clear investigation comment.
3. Include the evidence supporting your decision.
4. Follow the organization's escalation procedure when necessary.
5. Update the alert verdict.
6. Close the alert when the investigation is complete and closure is appropriate.

**Important:** Closing an alert as True Positive does not automatically stop the attack. Containment and remediation must follow the organization's incident response procedures.

## 10. Practical Takeaways

Alert triage is not simply about closing alerts. It requires understanding the activity, collecting evidence, and making a justified decision.

A good SOC L1 analyst should:

1. Follow a consistent investigation process.
2. Understand the affected user and asset.
3. Review relevant logs and surrounding events.
4. Validate suspicious indicators.
5. Avoid making decisions based only on alert names.
6. Document findings clearly.
7. Escalate genuine or complex threats appropriately.
8. Follow organizational procedures before closing alerts.
